# ai-cli_kernel L4、L5 規格

初代 ai-cli_kernel 的 AI-Agent 化初始版本 = L3 + L4 + L5。L3（`develop` 範本）已完成。這份規格是 L4、L5 的工作依據，分三個工作包，依序做。

## 共通規則

- 所有程式放 `src/ai-cli_kernel/`。不可修改 `src/core/`、`src/agents/`、`src/models/`、`src/plugins/`。做不到就停下來回報，不要繞。
- 對外名稱帶前綴：CLI `ai-cli kernel ...`、MCP `ai-cli_kernel_*`、匯出函式 `aiCliKernel*`。
- 沿用既有寫法：事實以日誌為準，`replay.ts` 是純函式，I/O 透過 `loop.ts` 的 deps 注入，測試可以換成假的。
- 測試加在 `tests/verify-ai-cli_kernel.mjs` 和 `tests/verify-ai-cli_kernel-e2e.mjs`。只用 stub，不呼叫真模型，不碰真實的排程器和遠端。遠端一律用暫存的 bare repo。
- 每個修補或防線在 `tools/mutations.json` 加突變：`from` 從當前原始碼取、只命中一處，`expect` 是斷言名稱的子字串。
- 每個工作包更新 `CHANGELOG.md`、`docs/ai-cli_kernel/技術手冊.md`。教學手冊只寫使用面，寫給不懂 git 的人看。
- 文件不可出現個人路徑（CONTRIBUTING §6）。
- worker 不 push、不動其他分支、不開子 agent、不呼叫 ai-cli。改動由 kernel commit。

## 工作包一：L4（回復點與單次放行）

### A. 開工前的回復點

使用者的要求：開工前先 commit＋push，寫壞了可以 rollback。

**不動使用者的分支、index、工作樹**，也不推使用者的分支：這個 repo push master 等於部署到所有機器。回復點是專用分支 `ai-cli_kernel/checkpoints/<runId>`。

委任書新增 `develop.checkpoint`：

```ts
{ mode: 'push' | 'local' | 'off'; remote: string | null; ref: string }
```

- 預設：有 `origin` 就是 `push`，沒有就是 `local`。CLI `--checkpoint push|local|off`。
- `off` 只有人手動核准的 run 能用，觸發的 run 不行。
- 委任書和狀態要顯示：會推到哪個遠端、哪個分支。

流程，在 `workspace_ready` 之前，由 `loop.ts` 呼叫 `WorkspaceOps`：

1. 用暫存 index 建快照，含未提交和未追蹤的檔案，遵守 `.gitignore`：`GIT_INDEX_FILE=<暫存> git read-tree HEAD`、`git add -A`、`git write-tree`。tree 和 HEAD 相同就直接用 HEAD，否則 `git commit-tree -p HEAD`。
2. `git update-ref refs/heads/<ref> <commit>`。
3. 模式是 `push`：先查快照相對 HEAD 改動的路徑，符合 `.env`、`*.pem`、`*.key`、`id_rsa`、`credentials*`、`*secret*` 就停下來，狀態 `waiting_human`、原因 `checkpoint_secret_risk`，**不可以推**。
4. `git push <remote> <commit>:refs/heads/<ref>`。不可帶 force。失敗就 `waiting_human`、原因 `checkpoint_push_failed`。人核准繼續時改成只留本地，並寫進裁決。
5. 記事件 `{ type: 'checkpoint', commit, ref, pushed, remote }`。

當掉重來要能接續：ref 已存在就驗證它，不重做。

其他要求：

- `refsChanged()` 要排除回復點分支和它的 remote-tracking ref，否則每次都會誤判。
- 交付前確認回復點 ref 還指向原本的 commit，被動過就是驗收失敗。
- 報告和裁決要列出回復點。
- `ai-cli kernel rollback <run>`：**只做不會丟東西的事**。預設印出 `git switch -c restore/<run> <commit>` 讓人自己跑；`--apply` 只建分支 `restore/<run>`，不切換、不動工作樹。不可以用 reset 或覆寫。

### B. 不可逆動作的單次放行

- `ai-cli kernel release create <run> --action merge|push --target <branch> --confirm <commit 前 10 碼> [--remote origin] [--hours 1]`
- `ai-cli kernel release run <id>`
- 只能對 `completed` 的 develop run 建立。
- 紀錄存 run 目錄的 `releases.jsonl`：`{ id, action, target, remote, commit, baseCommit, targetCommitAtCreate, expiresAt }`。
- `--confirm` 對不上交付的 commit 就拒絕，確保人看的就是這一版。
- 執行前全部重驗：沒用過、沒過期、分支 HEAD 等於 commit、測試通過的是這個 commit、target 現在還是 `targetCommitAtCreate`。
- 先記意圖再執行。結果不明就標 `unknown`，**絕不自動重試**。
- `merge`：repo 目前就在 target、工作樹乾淨，才 `git merge --ff-only`。否則拒絕並說明。
- `push`：`git push <remote> <commit>:refs/heads/<target>`，不可帶 force。target 是遠端預設分支時要另外加 `--allow-default-branch`，訊息要寫明這可能等於部署。
- **不提供 MCP 工具，只有 CLI**：放行是人的決定。觸發的 run 不能建立放行。

### 驗收

回復點包含未提交與未追蹤的檔案，而主目錄的 HEAD、index、工作樹完全不變；被忽略的檔案不進快照；疑似秘密檔不推；push 失敗會停；當掉重來不重複；回復點被動過驗收失敗；rollback 不動工作樹；放行的 confirm 不符、過期、重複使用、HEAD 變動、target 漂移都拒絕；放行不帶 force。

## 工作包二：L5（委任範本與主動觸發）

### 委任範本

存在 `kernelStateDir()/mandates/<name>.json`：

```ts
{ name, input: KernelStartInput, approval: { digest, approvedAt, expiresAt } | null, limits: { maxRunsPerDay, maxInputTokensPerDay } }
```

- `ai-cli kernel mandate save <name> ...`：選項和 `start` 相同，多 `--max-runs-per-day`（預設 1）、`--max-tokens-per-day`（預設 4000000）。覆寫內容會讓核准失效。
- `ai-cli kernel mandate approve <name> --acknowledge-unisolated [--days 30]`：只有 develop 要承認未隔離。**預設 30 天過期**，今天的同意不能變成長期授權。
- `mandate list`、`mandate show <name>`、`mandate revoke <name>`。
- 核准只有 CLI，不提供 MCP 工具。列表可以有 MCP 工具。

### 主動觸發

- `ai-cli kernel triggers on|off`：總開關，**預設關閉**。
- `ai-cli kernel trigger <name>`：一次性指令，跑完就結束，沒有常駐程式、不開 port。依序檢查，任何一項不過都記下原因並結束，不排隊、不重試：
  1. 總開關開著
  2. 不是 worker 環境（`assertCanStartJob`）
  3. 範本有核准、digest 對得上、沒過期
  4. 今天的次數和 token 沒超過上限（帳本 `kernelStateDir()/triggers.jsonl`）
  5. 沒有別的 run 佔著鎖
- 都過了就建 run 並核准啟動，委任書記 `origin: { kind: 'trigger', mandate, digest }`。
- 觸發的 run：`checkpoint.mode` 不可以是 `off`；模式是 `push` 時回復點沒推成功就停（這是使用者明確的要求）。
- 觸發時若 repo 有 `.codex/hooks.json` 且 worker 是 Codex，在 run 的註記裡寫明專案層 hook 可能不生效。
- `ai-cli kernel schedule <name> --daily HH:MM | --every-hours N`：預設只印出要跑的指令。加 `--apply` 才真的登記：Windows 用 `schtasks`，工作名稱 `ai-cli_kernel_<name>`；POSIX 只印 crontab 那一行，不代為修改。`schedule <name> --remove` 移除。
- 測試注入假的執行函式，不可以真的呼叫 `schtasks`。

### 驗收

總開關關著不跑；沒核准、過期、內容被改過都不跑；每日上限生效；鎖被佔用時跳過並記錄；worker 環境不能觸發；觸發的 run 不能用 `checkpoint off`；回復點失敗就不派 worker；`schedule` 不加 `--apply` 不會執行任何東西；觸發的 develop 走到分支和報告，沒有合併、沒有 push 到回復點以外的地方。

## 工作包三：L5（記憶與歸檔包）

### 記憶

存在 `kernelStateDir()/memory/<repoKey>.jsonl`。`repoKey` 是 origin URL 的雜湊，沒有 origin 就用第一個 commit。

```ts
{ id, text, source: { kind: 'human' | 'run'; runId? }, scope: { paths?: string[]; template?: string }, status: 'candidate' | 'active' | 'revoked', createdAt }
```

- `ai-cli kernel memory list|add|promote|revoke`。
- decide 可以在 `finish` 或 `plan` 帶 `lessons: string[]`（最多 3 條，每條 500 字元）。**一律存成 `candidate`，模型不能自己升級。**
- 只有 `active` 且範圍符合的才給 decide，最多 20 條、4000 字元，放在 `<memory untrusted="true">`，並寫明只是參考。

### 讀 Knowledge（選配）

公開套件不能依賴私人服務，所以只做通用介面：委任書可帶 `contextCommand`。kernel 在開工前跑一次，輸出最多 8000 字元存進 outputs，放在 `<context untrusted="true">` 給 decide。失敗不擋開工，但要寫進日誌和報告。使用者可以自己接 Knowledge 的命令列。

### 歸檔包

使用者的要求：歸檔是最重要的收尾環節，kernel 的 run 不能漏掉。

kernel **不寫** Planner 和 Knowledge，只負責不讓東西漏掉：

- `buildArchivePacket(store)`：純函式，**從日誌現場算出來**，不依賴結束時有寫檔，所以當掉的 run 也歸得到。內容：runId、狀態與原因、目標、範本、repo、分支、基準與最新 commit、commit 清單、改動的檔案、測試指令與結果、失敗次數、用量、模型、每個步驟的標題與結果、回復點、放行紀錄、候選記憶、由狀態推導的下一步。
- 任何已結束或停住的 run 都算待歸檔，直到人標記。標記存 run 目錄的 `archived.json`。
- `ai-cli kernel archive list`（只列沒歸檔的）、`archive show <run>`、`archive done <run> [--note <文字>]`。
- MCP 工具 `ai-cli_kernel_archive_list`、`ai-cli_kernel_archive_show`、`ai-cli_kernel_archive_done`：主 session 歸檔時要用。
- `ai-cli kernel status` 不帶 run 時，第一行顯示待歸檔幾筆。觸發的 run 特別標出來。

### 驗收

候選記憶不會給 decide，升級後才會；撤銷立刻生效；記憶和 context 都標成不可信；範圍不符的不給；`contextCommand` 失敗不擋開工；歸檔包從日誌算出來，當掉的 run 也有；已歸檔的不再列出；模型的 lessons 不會自動變成 active；kernel 沒有任何路徑寫入 Planner 或 Knowledge。
